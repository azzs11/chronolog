# ChronoBench: evidence-locked incident stories

Can a small local model write an incident story that only says what the evidence shows? Generated by `uv run bench stories`; do not edit by hand.

## Setup

- **Model:** `qwen2.5:3b` on Ollama 0.40.17, temperature 0, running locally (cost $0). Run 3 times (model seeds 0, 1, 2): a local model does not repeat itself exactly.
- **Incidents:** 30 simulated incidents (6 faults x seeds 6-10), RootRank with the true start. Simulated because real RCAEval lines carry no ids to cite. Seeds 1-5 were used to write the prompt and the checker and are not reported here.
- **What the model sees:** the top 3 suspects and numbered facts (E1, E2, ...) that the engine computed, each backed by log ids; never raw logs. It must cite fact keys.
- **The checker drops a sentence** that cites nothing or an unknown key, names a service that is not a suspect, cites a fact about a service it does not name, uses a number not in its services' facts, or gives a reason ("due to", "suggesting", ...) the facts do not state.
- **Code:** fingerprint `fc03ca6c698ea14b`.

## Limits

- The checks are mechanical. A kept sentence can still read more into a fact than it says (seen on the dev seeds: "... indicating it was involved in the issue"). Kept sentences were not audited by people.
- A local model is not exactly repeatable, even at temperature 0 with a fixed seed, so the headline is a mean over runs and this report is not byte-identical when re-run. Times depend on the machine.
- A checker bug was found on the test split after the first report: fact keys written into a sentence ("... (E4).") counted as unsupported numbers. It was fixed and the benchmark re-run; before the fix, citation precision was 72.7% and 76.6% of sentences were kept.
- Simulated incidents have simple, repetitive messages; real logs are harder.
- Stories restate the ranking. If RootRank's top suspect is wrong, the story is wrong too, and says so only through the words "likely" / "possible".

## Examples (first run, every 6th incident)

**crash/gateway/6**

- kept: The gateway service started with a message stating it was version <*>.<*> and ready to start.
- kept: The gateway service began listening on a port indicated by the message.
- dropped (unsupported_cause): The gateway service received a message indicating it was shutting down due to receiving SIGTERM, which was not logged before.

**disk/auth/7**

- kept: The incident started with the auth service logging its first 502 error lines, and a new message indicating 'no space left on device while writing /var/lib/auth/wal-<*>.log'.
- kept: The gateway service also logged its first 502 error lines, along with a new message stating 'auth returned <*>'.

**memory/catalog/8**

- kept: The catalog service logged a message indicating a garbage collection pause lasting more than the threshold of <*>ms, which is a new occurrence.
- kept: The cart service did not log any error lines, new messages, or mention issues from other services.

**cpu/cart/9**

- kept: The gateway service first logged an error at the start of the incident (E1).
- kept: The gateway service also logged a new message: 'timeout calling cart after <*>ms' (E2).

**delay/db/10**

- kept: The cart service logged a message indicating slow response from the db service (195×).
- kept: The catalog service also logged a message indicating slow response from the db service (217×).
- dropped (unknown_service): Other services mentioned the issue in 596 log lines during the incident.
