# ChronoBench: robustness to lost logs and clock skew

Does RootRank survive messy logs? Generated by `uv run bench robustness`; do not edit by hand.

## Setup

- All 359 RCAEval cases, headline protocol: whole (system, root service) groups held out, 5 seeds, 25 boosting rounds. The model is trained on **clean** logs; only the held-out cases are degraded.
- **Dropped lines:** each log line is removed independently with the given probability.
- **Clock skew:** each service's clock is shifted by a whole number of seconds drawn uniformly from -2..+2 (timestamps are whole seconds); lines are then re-sorted by time. The injection time is unchanged.
- **Gaps (bursty loss):** every line in a window of 60 s at a random place is removed for all services, or every line of one random service in a window of 120 s (a collector outage; the faulty service itself can go silent). The gap falls at a random place, so it often misses the moment that matters; a gap that hides the faulty service exactly when it breaks would cost more than these numbers show.
- The seed changes which lines drop, which offsets are drawn and where a gap falls. Mean ± standard deviation over 5 seeds. First-error is degraded the same way. ChronoLog-H is not rerun here (each replay takes minutes).
